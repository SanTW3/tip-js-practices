## 1. Цель работы

Подключить браузерный интерфейс списка задач к учебному HTTP API: читать задачи и категории с сервера, создавать, изменять, отмечать и удалять задачи через `POST`, `PATCH`, `DELETE`, показывать состояния загрузки и ошибок и не допускать, чтобы устаревший ответ перезаписал новый. Данные теперь хранит сервер, а не `localStorage`.

## 3. Реализация

### 3.1. HTTP-клиент

`src/api-client.js` перенесён из ПР5 и расширен. `requestJson(path, { method, query, body, signal, timeoutMs })`:
- разрешены только `GET`, `POST`, `PATCH`, `DELETE`, метод приводится к верхнему регистру, иначе `TypeError`;
- `GET` с телом отклоняется до сетевого запроса;
- всегда отправляется `Accept: application/json`; при наличии `body` — `JSON.stringify(body)` и `Content-Type: application/json` (без тела этот заголовок не добавляется);
- тайм-аут (`AbortSignal.timeout`) и внешний сигнал (`AbortSignal.any`) сохранены из ПР5;
- сначала проверяется `response.ok` (HTTP-ошибка → `ApiError` с `status`, `code`, `details`, `url`), затем `204` → `null`, затем `Content-Type` и разбор JSON;
- виды ошибок: `http`, `network`, `invalid-response`, `timeout`, `aborted`.

### 3.2. Доменный API

`src/task-api.js`: `getTasks`, `getTaskById`, `getCategories`, `loadInitialData` (задачи и категории параллельно через `Promise.all`), `createTask` (`POST /tasks`), `updateTask` и `setTaskCompleted` (`PATCH /tasks/:id`), `deleteTask` (`DELETE /tasks/:id`, ожидается строго `null`), `resetDemoData` (`POST /debug/reset`). Последний аргумент каждого метода — `{ signal }`. Схема каждого ответа проверяется здесь же (`isTask`, `isCategory`, уникальность id, `meta.total`); ошибка схемы → `ApiError` вида `invalid-response`.

`src/form-validation.js`: `validateTaskDraft(draft, categories)` возвращает `{ valid, value, errors }` — название 1–100 после `trim`, приоритет из трёх значений, `categoryId` числом и только из загруженных категорий.

`src/task-view.js`: карточка `li.task-card[data-task-id]` с названием, статусом, приоритетом, категорией и кнопками `toggle`, `edit`, `delete`; весь текст через `textContent`, список заменяется через `replaceChildren`.

### 3.3. Состояния интерфейса

`src/app-controller.js`, функция `loadCurrentTasks`: перед запросом — `loading` (`aria-busy="true"`). После ответа: если задач нет — `empty` («По выбранным условиям задач нет.»), иначе `ready`. При ошибке — `error` с понятным текстом из `messageForError` и кнопкой повтора. Отмена (`aborted`) пользователю не показывается. Первая загрузка идёт через `loadInitialData` (задачи + категории); если она не удалась, кнопка повтора снова вызывает `loadInitialData`, а не `getTasks`.

### 3.4. Изменение данных

Все изменения идут через общую функцию `runMutation`: `setMutationPending(true)` блокирует кнопки → запрос к API → сообщение «… выполнено» → повторный `GET /tasks` с текущими фильтрами → `setMutationPending(false)` в `finally`. Список на экране всегда отражает ответ сервера. При ошибке показывается сообщение, блокировка снимается.
- создание: форма → `validateTaskDraft` → `api.createTask(value)` → форма очищается;
- редактирование: `beginEdit(id)` заполняет форму → `api.updateTask(id, value)`;
- смена статуса: `api.setTaskCompleted(id, !task.completed)`;
- удаление: подтверждение → `api.deleteTask(id)`;
- сброс: `api.resetDemoData()` и перезагрузка с текущим фильтром.

### 3.5. Защита от устаревшего ответа

Перед каждой загрузкой предыдущий `AbortController` отменяется, создаётся новый, а счётчик `loadNumber` увеличивается. Ответ применяется только если его номер равен последнему `loadNumber`. Так даже запрос, который не отреагировал на отмену, не перезапишет новый фильтр (проверено модульной проверкой 27).

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` не отклоняет Promise при ответе 404?**
   Для `fetch` 404 — это успешно полученный HTTP-ответ: соединение есть, сервер ответил. Promise отклоняется только когда ответа нет (сеть, отмена). Поэтому клиент сам проверяет `response.ok` и превращает такой ответ в `ApiError` вида `http`.
2. **Почему ответ 204 нельзя разбирать вызовом `response.json()`?**
   У 204 нет тела, `json()` пытается разобрать пустую строку и бросает `SyntaxError`. Поэтому клиент возвращает `null` до чтения тела.
3. **Чем состояние `empty` отличается от `error`?**
   `empty` — запрос успешен, просто задач по условиям нет; это нормальный результат. `error` — запрос не удался, показывается причина и кнопка повтора.
4. **Зачем отменять предыдущий запрос при смене фильтров?**
   Старый запрос может ответить позже нового и перезаписать актуальный список. Отмена экономит работу, а проверка номера загрузки гарантирует, что устаревший ответ не применится.
5. **Почему после мутации список повторно запрашивается у API?**
   Сервер — источник истины: он назначает id и может изменить данные. Повторный `GET` с текущими фильтрами показывает подтверждённое состояние и сразу учитывает фильтр (например, выполненная задача исчезает из «невыполненных»).

## 7. Вывод

Интерфейс разделён на три слоя: `api-client.js` отвечает за HTTP (методы, тело, статусы, ошибки), `task-api.js` — за маршруты и схему данных задач, `app-controller.js` — за состояние интерфейса и порядок действий, а `dom-app.js` только рисует и передаёт события. Контроллер не обращается к `document`, поэтому проверяется без браузера. Данные хранятся на сервере: после каждого изменения список запрашивается заново. Пройдены 23 + 33 + 14 Node-проверок и 13 из 14 браузерных; одна браузерная проверка падает из-за ошибки в её коде (`requireNode` внутри `waitFor`), сам сценарий создания проверен вручную и работает.
